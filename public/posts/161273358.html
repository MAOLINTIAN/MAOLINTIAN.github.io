按照我之前的学习习惯，在具体到一个模块时先明确其在整体中的定位，所以要先有整体，然后逐步深入到大的业务方向，最后再到自己负责的模块，这样比较好融会贯通，所以整体分为三篇

  • 第一篇： 主要学习未来企业在 AI 时代背景下一些开发模式的变化；企业业务能力的开发方向，更具体的是未来产研的精力会更多的投入到哪里，也就是人才的流动方向、研发资源的流动方向，我们以后的关注重点在哪儿。AI 时代产研大趋势 + 架构变革 + 人力流向（全局视野）
  • 第二篇： 在正式学习 CMDB 之前，先要了解其在整个企业信息化体系中的一个定位，即整个企业信息化体系要包含哪些模块和能力，以及CMDB 和 CSDM 在其中发挥什么作用。 企业整体信息化大盘 → 锚定 CMDB/CSDM 定位（找准自身位置）
  • 第三篇： 深入到 CMDB 、 CSDM去了解其中的核心逻辑和核心实践。 深耕 CMDB、CSDM 核心原理与落地（专精学习）

接下来是第二篇，关于整个企业信息化大盘的服务范围以及CMDB究竟在哪儿发挥作用？

一 用哪些视角去切入企业信息化

首先明确用哪些视角去切入，按照以往对新平台的学习过程，往往是先了解能力地图，再了解业务流，然后再看如何建模，和商户平台的建设习惯类似了，经过与AI多轮对话，最终锚定了五个视角来 进行切入，总结为： 先认地图 → 再跟业务走 → 再认对象 → 再建数据 → 最后查六要素是否齐全：

视角要解决的问题日常在干什么
管理视角「IT 到底要管哪些事？」对齐能力版图，知道 CMDB 该支撑谁
流程实践视角「事平时怎么转？」跟工单/变更/发现走一遍，找读写点
技术域视角「现实世界有哪些类东西？」定 CI 大类、分层，别漏域别乱类
数据与信息视角「我怎么做成配置真相源？」主战场：模型、边界、集成、质量 ；怎么建模、入库、集成、治理
要素视角「这套东西能长期跑吗？」查组织/流程/工具/指标是否配套能长期运营？

其中要素视角是贯穿首尾的体检表——前面四步设计完了，用要素问：谁负责、流程是否强制、工具是否接上、指标是否考核。

1 管理视角 ——「全局能力地图」

视角目标： 推开一扇门，看整张 IT 管理大厦有几层、几间房。静态能力版图（有哪些块）

核心工作：

  • 不画 CMDB 表结构，先回答：企业 IT 要提供哪些管理能力？
  • 例如：事件、变更、资产、监控、安全、BCM、组合管理……分在战略 / 建设 / 运营 / 横切哪一层。
  • 关联：圈出 CMDB 主要服务的房间——通常是 R4 资产与配置，加上 R1–R3、D2 变更、X1–X3 等「强依赖配置关系」的房间。

产出物： 能力域清单、依赖强度（高/中/低）、和业务的边界说明。

管理视角 = WHAT（管什么能力），还不是 HOW（怎么流转、怎么存）。

2 流程实践视角 ——「业务平时怎么转」

视角目标： 站在服务台/变更专员旁边，看一张 动态流转图——谁发起、谁审批、什么时候结束。静态能力版图（有哪些块, 管理是 地图，流程是 地图上走的路线）

核心工作：

  • 在管理视角的「房间」里，换成 ITIL 实践语言：事件、变更、问题、SACM、发现……
  • 对每个实践标：什么时候读配置数据？什么时候写？谁负责写？
  • 关联：CMDB 的价值不在库里躺着，而在流程转的时候被用起来——影响分析、变更后回写、发现入库。
  • ITSM 在哪？ ： ITSM 不是单独一层视角，而是 流程实践的载体（工具+流程实现）。

产出物： 实践 × Read/Write CMDB 矩阵、变更闭环是否强制回写。

流程实践视角 = HOW work flows（事怎么转），决定 CMDB 何时被消费和生产。

3 技术域视角 ——「世界上要管哪些类型的东西」

视角目标： 像在做 领域模型前的名词盘点——网络、服务器、应用、数据库、云资源、安全设备……各长什么样。现实世界分几类名词（偏领域分析）

核心工作：

  • 按 技术分层 列域：计算、网络、存储、应用、中间件、云、终端、安全等。
  • 定 CI 类型空间：每一域有哪些 Class、关键属性、常见关系（运行在、连接到、包含）。
  • 避免 CMDB 变成一个大杂物表。

CSDM 在不在这一层？ ： 只有一部分在。

  • 技术域视角：偏 「技术组件怎么分类、怎么分层」（Infrastructure / Application 等技术侧）。
  • CSDM 完整语义（Business Service → Application Service → Application → Infrastructure）：主战场在 ④ 数据与信息视角的「配置与服务模型」，因为那是 业务服务到技术的映射规则，不只是「网络算网络、服务器算服务器」。

技术域视角 = 管什么类型的对象（名词表+分层）；CSDM 的「服务→技术」语义在数据视角里定稿。

4 数据与信息视角 ——「怎么做成配置数据源」

视角目标： 从「认对象」进入 「定规则、建库、接管道、保质量」。这些名词如何变成模型、入库、集成、治理（偏方案与实现）, 先技术域列全 → 再在数据视角里定 CSDM 规则与 CMDB schema

核心工作：

子块日常在干什么
A. 配置与服务模型CSDM/BTM：服务、Offer、App、Tech 怎么连；和流程里的 Service、Change 对象怎么对齐
B. 数据域与治理CMDB 管什么、不管什么；质量 KPI；Steward；基线、审计
C. 集成与数据流Discovery、云 API、变更回写、ITSM/ITOM 消费；去重、主键、时效

CMDB 在哪？

CMDB = 本视角的核心实现（配置与关系数据的存储与关系引擎），不是管理视角里的一个「业务能力名」，而是 R4 等能力在数据层的落地。

数据与信息视角 = 对象怎么建模、怎么写入、怎么存储、怎么被消费、怎么治理质量。

5 要素视角 ——「横切体检：能运营吗」

视角目标： 不是再画一张新地图，而是拿着 六要素 checklist 问：前面设计的东西，公司真跑得起来吗？

核心工作：对 每一个支撑的能力（如变更管理、SACM）或 CMDB 本身 考核：

要素对 CMDB 架构师的日常含义
① 组织有没有配置管理员、数据管家？变更谁回写？
② 流程SACM 有没有？变更后是否强制更新？
③ 数据模型、质量规则
④ 工具CMDB、Discovery、ITSM 是否集成
⑤ 指标完整率、关联率是否进考核
⑥ 伙伴厂商发现、云、外包谁提供数据

要素视角 = 不是新业务流，而是「组织/流程/数据/工具/指标/伙伴」是否配套，防止只做模型没人管、有库无流程。

管理定范围 → 流程定触点 → 技术域定对象 → 数据定方案 → 要素定能否长期运营。

二 管理视角：SDRG 十六能力域与 CMDB 聚焦

做 CMDB 或配置数据方案之前，需要先有一张 能力地图。否则容易掉进细节：表怎么建、接口怎么接，却不清楚 在支撑哪块 IT 管理职责。管理视角只做一件事：划定 企业 IT 应具备的管理能力，不涉及流程怎么转、CI 怎么分、CMDB 怎么建——那些分别在流程、技术域、数据视角中展开。

项内容
对齐需求时判断「这是事件、变更、资产，还是安全、BCM」——先把需求归到正确的管理域
划范围时明确本期方案覆盖哪几块能力域，不贪大求全
沟通时用业务和管理语言对话（“故障影响范围”“变更风险”“灾备恢复优先级”），而不是一上来就讲配置项和数据库字段

企业 IT 管理能力分为 四大类、十六个能力域：

大类代号定位
战略与组合S定方向、配资源、对业务
建设与设计D建系统、改环境、定服务
运营与保障R日常跑服、响应、稳态运营
治理与韧性G安全、合规、连续、改进（贯穿 S/D/R）

共同特征： 决定 做什么、先做什么、花多少钱、对业务承诺什么；周期偏长，非一线灭火。

能力域定义管理什么关键概念典型产出配置数据相关度

S2 投资组合与需求集中管理投资与需求优先级项目组合、应用组合、需求 backlog、路线图、技术债务PPM、APM组合看板、路线图中
S3 业务关系与价值与业务协作，管理服务预期与价值业务对接、服务评审、满意度、成效汇报BRM、SLM评审纪要、价值报告低

共同特征： 通过 项目、变更、架构、服务定义 改变或新增 IT 能力；强调 可控上线。

能力域定义管理什么关键概念典型产出配置数据相关度

协作关系与 CMDB 聚焦

纵向： S 定方向与资源 → D 建设与定义服务 → R 日常运营；G 贯穿 S/D/R。

横向（常见链路）：

场景能力域
新系统上线S2 → D2 → D1 → D3 → D4 → R4 → R3
生产故障R3 → R1 → R2 → R4
安全漏洞G1 → R4 → D3
服务评审S3 → D4 → R1 → G5

CMDB 架构师优先对齐： R4（主场）、D3 / R1 / R2 / R3 / D4 / G3（P0），G1 / G2 / D1 / S2（P1）。CMDB 不是第 17 个能力域，而是支撑 R4 并为上述高相关域提供配置与关系数据。

三 流程实践视角：分层流程、主链路与读写矩阵

流程实践视角： 承接管理视角的 S/D/R/G 能力域，说明"这些事通过哪些 ITIL 实践来执行、工单怎么流转，以及 CMDB 在哪一步被读、在哪一步被写"

项内容
干什么把 S/D/R/G 能力域落到 ITIL 实践 与 工单流转，说明这些事通过哪些流程执行、工单如何在环节间流转，以及 CMDB 在哪一步被读、在哪一步被写
日常怎么用接到需求 → 先判断属于哪条实践链（事件链 / 变更链 / 问题链 / SACM 链）→ 在方案中标出 CMDB 的读写触点
不做不定义 CI 类型（→ 交给 ③ 技术域视角）；不设计表结构与集成方案（→ 交给 ④ 数据与信息视角）；不做六要素成熟度体检（→ 交给 ⑤ 要素视角）

1 管理域 → 流程实践映射

管理域定义了"管什么"，流程实践定义了"怎么执行"。先把 S/D/R/G 落到具体的 ITIL 流程上：

管理域核心业务目标对应的流程实践
D3 变更发布与部署安全地改变 IT 环境变更管理、发布管理、部署管理
D4 服务设计定义服务标准与承诺服务目录、服务级别、服务设计
R1 服务台与履行快速响应用户服务台、事件管理、服务请求
R2 问题与修复找到根因并根治问题管理
R3 监控与运营持续感知系统状态监控与事件、可用性/容量管理
R4 配置资产与许可维护配置数据的唯一真实来源SACM、ITAM、SAM
G1 安全运营检测与响应安全威胁漏洞管理、安全事件响应
G3 业务连续性灾难后恢复业务BCM、DR、演练
G4 知识管理经验可复用知识管理（KCS）
G5 持续改进越来越好度量、复盘、改进项跟踪

2 流程分层：三个运转节奏

IT 流程按节奏分为三层。这张分层图是"链上找触点"的基础——不同层对 CMDB 的读写模式完全不同：

层级节奏特征核心流程CMDB 交互模式
L1 战略与组合低频、决策型组合评审、需求立项、预算审批读报表/看趋势，不直接写
L2 建设与设计中频、项目型架构评审、项目交付、变更/发布/部署、服务目录发布变更后必回写，服务定义写入
L3 运营与保障高频、持续型监控告警 → 事件/请求 → 问题 → SACM/资产 → 容量/可用性读影响分析，发现自动入库
L4 治理与韧性横切嵌入安全响应、合规审计、BCM 演练、知识/改进读依赖链/历史，审计读基线

关键关系： L1 决策驱动 L2 建设，L2 交付物进入 L3 持续运营，L4 横向嵌入所有层（不算到核心运转层）。

日常运维最核心的六步闭环，每条链路上 CMDB 的读写时机是确定的：

控制变更管理安全改环境已实施 Change读前评估 + 写后更新

沉淀知识管理可复用Knowledge Article关联 CI 标签（轻量）

4 CMDB 读写情况与触点关联

把上面的每个实践拆开，明确"读什么、写什么、强度多大"：

实践读 CMDB（查询）写 CMDB（更新）强度
事件管理影响范围、服务依赖、优先级故障 CI（可选标记）高
问题管理CI 故障历史、依赖关系一般不写高
变更管理变更前影响范围评估实施后必须回写最高
发现/服务映射—自动入库（高吞吐）最高
SACM审计比对、基线查询权威维护（增删改）最高
ITAM/SAM资产状态、许可证用量同步资产实例/状态高
BCM/DR依赖链、恢复优先级一般不写最高（读）

三条硬规则（研发侧必须遵守）：

  1. 变更必回写：变更实施后，CMDB 中对应 CI 的属性和关系必须同步更新
  2. 能发现不手工：CI 数据优先由 Discovery/Service Mapping 自动填充，禁止手工录入可自动发现的数据
  3. 告警必关联 CI：所有监控告警必须携带 CI 标识，否则无法触发影响分析和自动分派

5 ITSM 与 CMDB 的关系

ITSM 负责承载工单流转与审批，它引用 CMDB 中的 CI 数据，但不替代 CMDB。

关注三个集成点：

  • 强制关联 CI：事件单/变更单必须关联至少一个 CI，否则无法提交
  • 关闭触发回写：工单关闭时，自动触发 CMDB 状态/属性的同步更新
  • CAB 影响分析：变更顾问委员会审批时，直接调用 CMDB 的影响分析 API

管理定域，流程定链；链上找触点，触点定 CMDB 读写。

3 典型关系定义

关系是 CMDB 区别于资产台账的核心。以下五种关系覆盖了绝大多数场景：

关系类型语义方向典型场景
包含上下级组成父 → 子集群包含 Pod、VPC 包含子网
运行在部署位置上 → 下应用运行在主机、DB 运行在存储
连接到网络/数据连接双向应用到数据库、微服务到微服务
依赖于服务可用性依赖下游 → 上游业务服务依赖应用服务、应用依赖中间件
分配给资产归属设备 → 人笔记本分配给用户、服务器分配给团队

建模提示：

  • "包含"和"运行在"的区别：前者是强组成关系（删父必删子），后者是部署关系（迁移不删）
  • "依赖于"是故障影响分析的核心关系，必须精确维护
  • "连接到"通常由 Discovery 自动生成，不手工维护

4 分层建设优先级

不要追求一步到位，按优先级渐进覆盖：

优先级范围具体动作原因
P0计算 + 应用 + 网络 + “依赖于”建核心三类 CI 和依赖关系覆盖80%的故障影响分析和变更评估场景
P1云标签归属 + 容器层级补云资源、K8s 对象（Pod/Cluster）云原生场景下的资产可见性
P2安全 + 机房 + 终端按项目范围按需扩展特定领域需求驱动，非全局必选

判断一个 CI 类该不该进 CMDB 的三问：

  1. 故障时，需要知道它影响谁吗？
  2. 变更时，需要评估改它的风险吗？
  3. 合规/审计时，需要证明它的配置状态吗？

三问任一为"是"，就应该纳入。

2. CMDB 边界（明确什么该进、什么不该进）

✅ 属于 CMDB❌ 不属于（仅存关联）
CI 的唯一标识与核心属性全量的监控时序数据（如每秒 CPU 使用率）
CI 之间的关系（依赖、包含、连接）工单的全文描述、客户对话记录
服务 → 技术组件的映射关系财务总账、采购合同扫描件

要素视角的基本定位：

项内容
干什么用 六要素 检查能力域或 CMDB 项目能否真正落地并长期运营，而不是建完就废

1 六要素详解

六要素是 CMDB 项目从"能用"到"好用"的六个必要条件，缺任何一个都会让前面的设计打折扣。

① 组织——谁负责、谁决策

管配置数据，首先要有人。配置管理员负责 CMDB 数据的日常维护和审计，Data Steward 负责数据质量标准的制定和争议仲裁。组织要素要回答的是一串 RACI 问题：谁对 CI 数据的准确性负责？变更后谁来回写 CMDB？数据出问题找谁？如果这些问题没有答案，CMDB 很快就会变成没人敢用的"鬼库"。

缺了组织会怎样？数据无人认领，质量无人负责，CI 属性过期了也没人发现。

② 流程——怎么做、如何审批

有了人，还要有章法。流程要素的核心是把 CMDB 的维护动作嵌入到日常 ITIL 流程里，而不是让维护 CMDB 变成一项独立的工作。SACM 流程定义了 CI 的创建、更新、删除和审计规则。变更管理流程里必须嵌入"变更实施后强制回写 CMDB"的步骤——不是靠自觉，是靠流程强制。

缺了流程会怎样？CMDB 数据只减不增，越用越烂，半年后准确率跌破 50%。

③ 数据——管什么信息

数据要素定义了 CMDB 里存什么、怎么存。CI 类型有哪些、每个 CI 该有哪些属性、属性之间有什么校验规则、数据质量的标准是什么。这些在④数据与信息视角里有详细设计，要素视角要做的是检查——这些东西是否被正式定义、是否有文档、是否被团队理解。

缺了数据会怎样？只有工具没有标准，每个人按自己理解往 CMDB 里填，格式不统一、字段乱填，查询时谁也找不到想要的信息。

④ 工具——用什么系统

工具是承载组织、流程和数据的平台。CMDB 本身是核心存储，Discovery 负责自动发现和写入，ITSM 系统在事件/变更/问题流程里读写 CMDB 数据。要素视角检查的是——这些工具之间是否真的打通了，数据能不能自动流转，而不是靠手工导出再导入。

缺了工具会怎样？CMDB 变成信息孤岛，发现工具扫出来的数据和 ITSM 里用的数据是两套，谁也不信谁。

⑤ 指标——如何考核

没有度量就没有改进。指标要素定义了什么算"好"——CMDB 数据的完整率（必填字段是否填了）、关联率（CI 之间的关系是否建立了）、及时率（变更后多久回写 CMDB）、准确率（随机抽查与实际情况是否一致）。这些指标要有人盯、有人被考核，否则设计再好的流程也会退化。

缺了指标会怎样？无人有动力维护数据质量，"能用就行"的心态蔓延，数据质量持续下滑无人察觉。

⑥ 伙伴——内外部依赖

IT 环境里不是所有 CI 都在自己掌控中。云厂商的资源配置、外包团队的资产录入、硬件厂商的维保信息，这些外部数据源的质量直接影响 CMDB 的可靠性。伙伴要素要回答——谁对这些外部数据的准确性负责？合同里有没有约定数据交付的标准和时效？

缺了伙伴会怎样？源数据不可靠，CMDB 再怎么维护也是建立在沙滩上的城堡。

六要素之间的闭环关系：

组织定义了"谁来做"，驱动流程的设计。流程规定了"怎么做"，对数据提出质量要求。数据标准落地到工具里，由工具承载和自动化。工具的运行效果通过指标来衡量，暴露短板。伙伴作为外部输入，影响整个链条的可靠度。六个要素互为前提，形成闭环。

2 六要素 × 管理域（示例）

同一个六要素，在不同管理域里会有不同的具体内容。以下以两个核心管理域为例：

R4 配置与资产管理域：

组织方面，需要明确的配置管理员和资产管理员角色，以及两者的职责边界。流程方面，核心是 SACM 流程和定期配置审计流程。数据方面，CMDB 和资产台账是核心数据资产，两者的数据必须一致。工具方面，CMDB 和 Discovery 是主力工具。指标方面，关注 CI 完整率和准确率。伙伴方面，硬件厂商的维保数据、云厂商的资源清单是主要外部依赖。

D3 变更发布与部署域：

组织方面，CAB（变更顾问委员会）和变更经理是核心角色。流程方面，变更审批流程和紧急变更通道是重点。数据方面，变更影响分析所依赖的 CI 关系数据是核心。工具方面，ITSM 的变更管理模块与 CMDB 的集成是关键。指标方面，变更成功率是核心考核指标。伙伴方面，供应商的变更窗口和通知机制需要合同约束。

3 与其它视角的关系

要素视角是五视角系列的收尾，与前面四个视角的关系如下：

  • 管理视角（①）定义了要管哪些能力域。要素视角追问——每个域都有人负责吗，有流程吗，有指标吗？
  • 流程实践视角（②）定义了工单怎么流转、CMDB 在哪读写。要素视角追问——这些读写动作被流程强制了吗，还是靠自觉？
  • 技术域视角（③）定义了 CI 类型空间。要素视角追问——这些 Class 的数据质量标准定义了吗，由谁维护？
  • 数据与信息视角（④）定义了模型和集成方案。要素视角追问——集成跑起来了，但数据进来之后有人校验吗，不准确怎么办？

七 ITSM、CMDB、CSDM 三层关系收束

这三者的关系，用一句话说清楚：**CSDM 是骨架，CMDB 是血肉，ITSM 是动作。**它们不是平级关系，而是从抽象到具象、从数据到行为的三层依赖。

1 CSDM 是什么？——“数据的组织架构图”

CSDM（Common Service Data Model，通用服务数据模型）不是数据库，不是产品，而是一套标准化的数据建模框架。它回答：IT 世界里有哪些东西（业务服务、应用、服务器、网络……），这些东西之间应该怎么关联，以及每个东西该叫什么名字。

打个比方：CSDM 就是城市规划局发布的"城市分区规范"——住宅区、商业区、工业区分别在哪，主干道怎么连。它只管规则，不建房子。

CSDM 的核心价值是统一语言。没它之前，A 团队管服务器叫"主机"，B 团队叫"物理机"，C 团队叫"Server"；A 认为"应用"包含"服务"，B 反过来。所有人都在说同一件事，但互相听不懂。CSDM 就是那本"标准术语和关系手册"，让所有人对齐。

2 CMDB 是什么？——“按规则存数据的地方”

CMDB（Configuration Management Database，配置管理数据库）是实际的存储系统，里面存着一个个 CI（配置项）以及它们之间的关系。

CMDB 和 CSDM 的关系是：CSDM 画蓝图，CMDB 按蓝图盖楼。 CSDM 说"业务服务应该依赖应用服务，应用服务应该运行在服务器上"，CMDB 就按照这个规则建表、存数据、查关系。一个 CMDB 好不好，很大程度上取决于它有没有遵循一套清晰的数据模型——而 CSDM 就是业界最成熟的模型之一。

3 ITSM 是什么？——“用数据干活的动作层”

ITSM（IT Service Management，IT 服务管理）是一整套管理流程和工具平台，处理日常 IT 工作：用户报故障（事件管理）、查根因（问题管理）、上线新功能（变更/发布管理）、员工申请设备（服务请求）等等。

ITSM 和 CMDB 的关系是：ITSM 消费 CMDB 的数据来做决策，执行完后又把结果写回 CMDB。 比如：

  • 事件来了 → ITSM 读 CMDB 的 CI 关系图，判断影响范围
  • 变更执行完 → ITSM 把 CMDB 里对应 CI 的状态和属性更新掉
  • 用户申请笔记本 → ITSM 在 CMDB 里新建一个资产 CI 记录

ITSM 不存 CI 数据，它只是引用和更新 CMDB。CMDB 是"大脑"，ITSM 是"四肢"。

层次是什么核心问题比喻
CSDM数据建模框架“数据应该怎么组织和命名？”城市规划规范
CMDB实际数据库“具体的 CI 和关系存在哪里？”按规范建的房子
ITSM流程与工具平台“日常 IT 工作怎么流转和执行？”人在房子里干活

链式关系：CSDM 指导 CMDB 怎么建 → CMDB 存储 CI 和关系 → ITSM 消费 CMDB 数据来跑流程 → 流程执行结果回写 CMDB 。

总结一下

为了能全面的理解企业信息化的内容以及CMDB在其中的位置，我尝试从架构设计的逻辑的多个视角去看待整个信息化平台。管理视角先画出静态能力地图，知道IT要管战略、建设、运营、治理四大类十六个域，其中R4配置与资产就是CMDB要服务的主场（能力地图）。流程实践视角把能力落到ITIL流程上，看事件、变更、问题这些事怎么转，从而明确CMDB的读写触点——变更后必回写、发现自动入库、告警关联CI，这三条是硬规则（业务流）。技术域视角回到现实世界，把基础设施从业务服务到网络设备按L1到L4分层，盘点CI类型和关系（依赖于、运行在、连接到），给建模打底（物理世界）。数据与信息视角是重点需要关注的，在这里定CSDM模型、画CMDB边界、管理配置与关系（模型世界）。要素视角拿组织、流程、数据、工具、指标、伙伴这六要素当体检表，问自己一句：这套东西能长期跑起来吗？（自检清单）。最后再理解几个核心概念之间的关系：CSDM 指导 CMDB 怎么建 → CMDB 存储 CI 和关系 → ITSM 消费 CMDB 数据来跑流程 → 流程执行结果回写 CMDB
