Redis的内存模型

Redis 采用单线程 Reactor 模型，即同一个主线程负责所有工作：

  • 网络 I/O 处理：监听连接、读取请求、写回响应。
  • 命令执行：解析请求并执行对应的操作。

这个单线程之所以能支撑高并发，关键在于 I/O 多路复用。

I/O 多路复用机制

传统阻塞 I/O 的问题

  • 每个连接需要一个线程，线程创建/切换开销大。
  • 线程阻塞在 read/write 上时，CPU 资源被浪费。

多路复用的核心思想

一个线程同时监控多个连接（文件描述符），只处理那些真正就绪的连接，空闲连接不消耗 CPU。

Redis 使用的高效实现（epoll/kqueue）

  • epoll（Linux） / kqueue（BSD/macOS） 是事件驱动的 I/O 多路复用器。
  • 工作流程：
    1. 将所有客户端连接注册到 epoll 实例上，关注可读事件。
    2. 主线程调用 epoll_wait 进入休眠，等待内核通知。
    3. 当某个连接有数据到达时，内核唤醒主线程，并返回就绪的连接列表。
    4. 主线程串行处理这些活跃连接：读取请求、执行命令、写回响应。
    5. 处理完后再次进入 epoll_wait 循环。

epoll 相比 select/poll 的优势

对比维度select/pollepoll
监控方式每次调用都要将全部 fd 传给内核（O(n)）内核维护监控列表，事件发生时回调通知（O(1)）
返回结果返回全部 fd，需遍历找出就绪的直接返回就绪的 fd 列表
扩展性随 fd 数量增加性能下降性能与活跃连接数相关，可支撑百万连接

为什么 Redis 选择单线程模型？

  1. 瓶颈不在 CPU，而在内存和网络：Redis 是内存数据库，操作速度极快（纳秒级），CPU 很少成为瓶颈。真正的瓶颈往往是内存大小和网络带宽。

  2. 避免多线程的复杂性：

    • 无锁竞争：单线程消除了加锁/解锁的开销，也避免了死锁问题。
    • 无上下文切换：不需要在多个线程间切换，节省 CPU 资源。
    • 数据天然一致：命令串行执行，无需考虑并发修改。

  3. I/O 多路复用已经解决了并发问题：单线程 + epoll 足以高效处理数万并发连接，没必要引入多线程。

Redis 6.0 的优化：多线程 I/O

随着 10Gbps 甚至更高带宽网卡的普及，网络 I/O 本身的开销开始成为新的瓶颈。这里需要明确：

  • 网络 I/O 消耗的是 CPU 时间（数据在内核空间与用户空间之间的拷贝、协议解析），而不是内存。
  • 当网络带宽足够高时，单线程处理网络数据拷贝的 CPU 开销会显著增加，甚至可能影响命令执行的吞吐量。

因此，Redis 6.0 引入了多线程 I/O：

  • 多线程处理网络读写和协议解析：使用多个 I/O 线程并行处理网络数据的接收、发送和解析，将这部分 CPU 开销分散到多个核心。
  • 命令执行仍然单线程：解析后的命令被放入队列，由主线程串行执行，保证了无锁和数据一致性。
  • 效果：提升了网络吞吐量，释放了主线程的 CPU 时间，让主线程更专注于命令执行。

总结：Redis 线程模型演进

版本模型说明
Redis 6.0 之前单线程（I/O + 命令执行）单线程 Reactor + epoll，极致简单高效
Redis 6.0 及之后多线程 I/O + 单线程命令执行I/O 线程负责网络读写和协议解析，主线程串行执行命令

Redis 始终秉持一个核心哲学：

  • 用单线程执行命令来保证简单和一致，避免多线程的复杂开销。
  • 用 I/O 多路复用来应对高并发连接，让单线程也能驾驭海量连接。
  • 只在网络 I/O 成为 CPU 瓶颈时，引入多线程 I/O 进行辅助，解除瓶颈的同时不破坏命令执行的单线程特性。
