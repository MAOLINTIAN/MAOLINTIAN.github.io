在分布式消息系统中，消息传递通常分为三种语义：

  • At most once：消息最多传递一次，可能丢失，但不会重复。
  • At least once：消息至少传递一次，不会丢失，但可能重复。
  • Exactly once：消息恰好传递一次，既不丢失也不重复。

Kafka 从 0.11.0 版本开始引入了对 Exactly-Once 语义的支持，主要通过幂等性生产者和事务性生产者来实现。但要真正达到端到端的 Exactly-Once，还需要 Broker 端的正确配置和消费者端的幂等处理。本文将全面剖析 Kafka 如何保证消息不丢不重，并按照“问题 → 解决方案”的结构，清晰呈现每一步的设计思路。

第一部分：如何保证消息不丢（At Least Once 的基础）

消息丢失可能发生在生产者、Broker、消费者三个环节。我们需要在每个环节都设置正确的机制。

1. 生产者端：确保消息成功发送

问题：生产者调用 send() 后，消息可能因网络问题未到达 Broker，或到达后因超时未收到确认而认为失败。如果没有确认机制，消息就会丢失。

解决方案：

  • 异步发送 + 回调确认：Kafka 的 send() 是异步的，返回一个 Future。通过注册回调（Callback）可以获知发送结果。
    producer.send(new ProducerRecord<>("topic", "key", "value"), (metadata, exception) -> {

     
    if (exception == null) {

     
        // 发送成功
    } else {

     
        // 发送失败，记录日志或重试
    }
});
  • 配置重试：设置 retries 为较大值（如 Integer.MAX_VALUE），并配合 retry.backoff.ms 让生产者在遇到可重试错误时自动重试。
  • 同步发送：对于关键消息，可调用 producer.send().get() 阻塞等待结果，但会降低吞吐量，不推荐在高性能场景使用。

2. Broker 端：多副本与确认机制

问题：消息到达 Broker 后，若 Leader 副本宕机且数据未同步给 Follower，可能导致消息丢失。例如，Leader 写入成功但未同步给 Follower 就宕机，新选举的 Leader 没有该消息。

解决方案：

  • 副本机制：设置 Topic 的 replication.factor ≥ 3，确保数据分布在多个 Broker 上。
  • ISR（In-Sync Replicas）：Kafka 动态维护一个与 Leader 保持同步的副本集合（ISR）。生产者可通过 acks 参数控制消息的持久化级别：
    • acks=0：生产者不等待任何确认，可能丢消息。
    • acks=1：Leader 写入本地日志即返回成功，不等待 Follower 确认。如果 Leader 随后宕机，消息可能丢失。
    • acks=all（或 -1）：Leader 等待所有 ISR 副本都写入成功后才返回成功。这是最安全的级别。
  • 最小同步副本：配合 min.insync.replicas 参数，要求至少指定数量的 ISR 副本确认。例如设置 min.insync.replicas=2，那么当 ISR 少于 2 时，写入将失败，避免数据只写入单一副本。
  • Unclean Leader 选举：默认情况下，Kafka 不允许非 ISR 副本成为 Leader，防止数据丢失。应保持 unclean.leader.election.enable=false。

3. 消费者端：手动提交偏移量

问题：消费者拉取消息后，若自动提交偏移量，但业务处理失败，则消息“丢失”（因为偏移量已提交，不会再消费）。例如，消费者拉取一批消息，处理到一半时宕机，偏移量已提交，重启后将从下一条开始消费，导致未处理完的消息丢失。

解决方案：

  • 手动提交：设置 enable.auto.commit=false，在业务处理成功后再手动提交偏移量。
    while (true) {

     
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {

     
        process(record); // 业务处理
    }
    consumer.commitSync(); // 处理完一批后手动提交
}
  • 确保幂等处理：由于可能发生重复消费（下文详述），业务逻辑需设计为幂等。

通过上述三层的防护，我们可以实现 At Least Once 语义——消息不会丢失，但可能重复。

第二部分：如何保证消息不重（Exactly-Once 的核心）

即使消息不丢，重复消息也可能发生。重复的原因主要有：

  • 生产者端：因网络超时、Leader 选举等原因导致生产者重试，Broker 可能收到多条相同的消息。
  • 消费者端：因消费者再平衡、手动提交失败等原因，导致同一条消息被消费多次。

解决消息不重的问题，需要分别从生产者和消费者两个层面入手。

生产者端：防止因重试导致的重复

问题：生产者重试如何导致重复？

当生产者因为网络超时、Leader 选举等原因没有收到 Broker 的确认（ACK）时，它会重试发送同一批消息。如果 Broker 实际上已经成功写入这批消息，那么重试就会导致 Broker 存储两份相同的数据。例如：

  1. 生产者发送消息批次 A。
  2. Broker 成功写入 A，但 ACK 在网络中丢失。
  3. 生产者超时后重试，再次发送相同的批次 A。
  4. Broker 再次写入 A，造成重复。

解决方案一：幂等性生产者（单会话内不重复）

原理：

  • 开启 enable.idempotence=true 后，每个生产者被分配一个全局唯一的 Producer ID（PID）。同时，对于每个目标分区，生产者会维护一个单调递增的 序列号（Sequence Number），从 0 开始，每发送一批消息就递增 1。
  • 生产者发送消息时，会在请求中带上 (PID, 分区, 序列号) 三元组。Broker 端为每个 PID 的每个分区缓存最近写入的 5 个（可配置）序列号。
  • 如果 Broker 接收到的序列号等于已写入的最大序列号 + 1，则正常写入；如果小于或等于已写入的最大序列号，则视为重复请求，直接返回成功但不实际写入。

解答疑惑：为什么重试时序列号相同？

  • 重试发送的是同一批次消息，因此使用相同的序列号。Broker 通过比较序列号发现重复，直接丢弃重试批次，保证数据不重复。

局限：

  • 仅对单个生产者会话内有效。如果生产者进程重启，PID 会改变，无法跨会话去重。
  • 仅保证单分区内不重复，无法实现跨分区的原子性。

解决方案二：事务性生产者（跨分区/跨会话的 Exactly-Once）

问题：幂等性生产者无法处理跨分区原子性和生产者重启后的重复问题。例如，一个业务需要原子地向两个分区写入数据，或者生产者重启后可能导致数据重复。

原理：

  • 事务性生产者需配置 transactional.id（逻辑生产者，由用户指定，应用层代码配置，由业务前缀 + 稳定实例标识（如实例序号）组成，在部署时确定，重启后不变）。Broker 端的事务协调器会为该 ID 分配一个 PID，并将映射关系持久化到事务日志中。
  • 当生产者以相同 transactional.id 重启时，协调器会检查之前是否有未完成的事务，并强制中止（abort）僵尸事务，然后允许新生产者使用相同的 PID 和序列号，从而继承状态，避免因重启导致的序列号断裂。
  • 事务性生产者支持将多个跨分区的消息作为一个原子事务提交：
    producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord<>("topic1", "key1", "value1"));
producer.send(new ProducerRecord<>("topic2", "key2", "value2"));
producer.commitTransaction();
  • 如果事务提交失败，协调器会回滚所有写入，确保原子性。

效果：

  • 跨会话幂等：生产者重启后仍能使用相同的 PID 和序列号，避免重复。
  • 跨分区原子性：要么全部写入成功，要么全部失败。
