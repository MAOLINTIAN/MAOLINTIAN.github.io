在Java并发编程中，集合类的安全性与性能一直是开发者关注的核心。从早期的Hashtable到ConcurrentHashMap的演进，从synchronized到ReentrantLock的多样化锁机制，背后都贯穿着一个共同的目标：在保证线程安全的前提下，最大化压榨CPU和内存资源，减少无谓的等待与管理开销。

本文将沿着这条主线，深入剖析：

  • HashMap在1.7和1.8中的数据结构变化与并发问题
  • ConcurrentHashMap从分段锁到桶锁的演进
  • ReentrantLock的核心特性（可重入、公平性、可中断、条件变量）及其在AQS中的实现
  • CAS无锁机制的原理与应用

通过这篇文章，你将理解这些技术背后的设计思想，以及它们是如何围绕“减少等待、减少管理性操作”这一核心思想展开的。

一、HashMap的演进：从死循环到红黑树

1.1 JDK 1.7：数组+链表，头插法埋下隐患

在JDK 1.7中，HashMap采用数组+链表的结构存储键值对。当多个key映射到同一数组下标时，以链表形式存储，插入新节点采用头插法（新节点插入链表头部）。

扩容机制：当元素数量超过阈值时，数组容量翻倍，并对所有元素重新哈希（rehash），迁移到新数组。迁移过程中，头插法会导致链表反转——原链表顺序A→B→C在新数组中变为C→B→A。

1.2 并发下的死循环问题

在多线程并发执行put操作并触发扩容时，头插法的反转特性与线程交叉执行结合，可能形成环形链表，导致后续get操作陷入无限循环，CPU飙升到100%。

死循环的形成原理（简化版）：

  1. 线程一执行到Entry<K,V> next = e.next;后挂起，此时e指向节点A，next指向B。
  2. 线程二完成扩容，将原链表A→B迁移为新链表B→A（头插法反转）。
  3. 线程一恢复执行，按自己保存的引用操作，导致A的next指向B，而B的next已指向A，形成循环。
  4. 此后任何查找该链表上不存在的key时，线程将永远在环中循环。

资源开销视角：这不是普通的性能损耗，而是逻辑错误导致CPU时间被无限吞噬，比任何管理性开销都更致命。

1.3 JDK 1.8的改进：尾插法 + 红黑树

  • 尾插法：扩容迁移时按原顺序将节点插入新链表尾部，保持链表顺序不变。这从根本上避免了多线程并发扩容时形成环形链表的可能性（但注意：HashMap依然非线程安全，并发下仍会数据覆盖，只是不再死循环）。
  • 红黑树化：当链表长度超过阈值（默认8）且数组容量≥64时，链表转换为红黑树，将最坏情况下的查找效率从O(n)提升到O(log n)。当树节点数小于6时，又会退化为链表，避免树结构占用过多内存。

资源开销视角：尾插法消除了死循环这一“CPU黑洞”；红黑树化用额外的内存维护树结构，换取查询时的CPU节省，是典型的空间换时间。

二 ConcurrentHashMap的演进：从分段锁到桶锁

2.1 JDK 1.7：分段锁（Segment）

设计思想：将整个哈希表分成多个Segment（默认16个），每个Segment继承自ReentrantLock，独立管理一小段HashEntry数组。put操作时，先定位到具体Segment，然后只锁住该Segment，其他Segment的数据仍可被其他线程并发访问。

优点：并发度从1提升到Segment数量（默认16），读写性能远优于Hashtable；get操作不加锁（通过volatile保证可见性），读性能极高。

缺点：并发度固定，无法随CPU核心数动态调整；结构复杂，内存占用较高。

2.2 JDK 1.8：CAS + synchronized + 桶锁 + 红黑树

设计思想：放弃Segment，采用与HashMap1.8一致的数据结构（数组+链表/红黑树），通过CAS + synchronized实现线程安全。

  • CAS无锁插入：若定位到的桶位为null，则通过CAS直接插入，无需加锁。
  • synchronized桶锁：若桶位不为空，则对桶位头节点加synchronized锁，然后操作链表或红黑树。只有同一桶位的操作才会被锁住，不同桶位完全并发。
  • 红黑树化：与HashMap1.8一致，链表过长时转为红黑树。
  • 多线程协助扩容：触发扩容时，多个线程可共同参与数据迁移，每个线程负责一部分桶位，通过ForwardingNode指引，大幅缩短扩容阻塞时间。

优点：锁粒度从“分段”细化为“桶位”，并发度随数组长度动态增加；读操作多数无锁，写操作只在桶头加锁，竞争极小；扩容并行化；红黑树化提升最坏情况查询性能。

2.3 对比总结

三 锁的分类：synchronized 与 ReentrantLock 的全面对比

在Java并发编程中，synchronized和ReentrantLock是两种最常用的锁机制。它们都提供线程安全性，但在设计理念、功能特性、实现原理和适用场景上存在显著差异。理解这些差异，能帮助你在实际开发中做出更合适的选择。

2 各维度详细解析

1. 可重入性

  • 相同点：两者都支持可重入。同一个线程可以多次获取同一把锁，避免死锁。
  • 实现差异：
    • synchronized：JVM在monitor对象中记录锁的持有线程和计数器，每次进入加1，退出减1。
    • ReentrantLock：基于AQS的state计数，同一线程每次lock()将state加1，每次unlock()减1，state为0时锁释放。

2. 公平性

  • synchronized：只支持非公平锁。线程获取锁的顺序不保证，可能发生“饥饿”（某个线程长期得不到锁）。
  • ReentrantLock：构造函数可指定公平性：
    • new ReentrantLock(true)：公平锁，线程按照请求顺序获取锁（FIFO）。
    • new ReentrantLock(false)（默认）：非公平锁，允许插队，吞吐量更高。

为什么需要公平锁？ 某些场景下（如任务调度）要求线程按顺序执行，避免优先级反转或长时间等待。

3. 可中断性

  • synchronized：线程在等待锁时不可中断。如果线程被阻塞在synchronized上，调用interrupt()不会唤醒它，只会设置中断标志；线程只有获取锁后，才能检测到中断。
  • ReentrantLock：提供lockInterruptibly()方法，允许线程在等待锁时响应中断。如果线程被中断，会抛出InterruptedException并停止等待。

示例：

// synchronized无法响应中断
Thread t = new Thread(() -> {

   
    synchronized(lock) {

    // 如果锁被占用，这里一直阻塞，无法响应中断
        // ...
    }
});
t.interrupt(); // 无效

// ReentrantLock可中断
try {

   
    lock.lockInterruptibly(); // 等待锁时如果被中断，立即抛出异常
} catch (InterruptedException e) {

   
    // 处理中断
}
